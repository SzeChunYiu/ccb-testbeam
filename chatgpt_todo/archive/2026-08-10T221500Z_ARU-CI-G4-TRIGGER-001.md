# ARU-CI-G4-TRIGGER-001 — Geant4-path routing into required MC Validation CI

## Atomic contract

Input: a Git change set and `.github/workflows/mc_validation_ci.yml`.  
Output: deterministic statement whether every `push` and `pull_request` containing a `geant4/**` path is routed to the workflow that defines branch-protection job `test`.  
Units: none.  
State variables: event type, changed path, workflow path filters, job identifiers, exact commit SHA, workflow-run identity/conclusion.  
Scientific meaning: material generator/config/source changes must not escape the repository's required static/Python validation lane. This atom does **not** assert compiled Geant4 validation.

Required invariant:

```text
∀ event ∈ {push,pull_request}: geant4/** ∈ on[event].paths
and test ∈ jobs
```

## Evidence inspected

- Protected `main` initially `d62075693df5e0f58b64078097ddc4ebea86d90f`; coordination PR #1193 exact head `516b7d2def1151916441c92142a6b355892956ff` passed MC Validation run `31437027034` and was squash-merged as `e4c924b901b37093f7b66eaf8d1d1dad07ea3498`.
- Current `mc_validation_ci.yml` requires job `test` but its pre-repair `push.paths`/`pull_request.paths` omit `geant4/**`.
- PR #1192 exact head `bef24345e815152e22523a44b708c4359ad2958f` changes only `geant4/src_patch/ScatteringGenerator.cc`, `.hh`, and `patch_scatter.py`; GitHub reports no workflow runs for that exact head.
- #1192 is also scientifically stale: its patch reintroduces `if(event->GetEventID()==0) EnsureFilesLoaded();`, undoing the per-instance first-use readiness already validated on main. Its separate pre-read file digest does not prove a digest of the exact consumed byte stream.
- `geant4/setup_and_run.sh` still uses an unpinned/reused external `hibeam_g4` checkout and reused `build_conda`, so even a routed green Python/static CI result cannot become executable provenance.

## Competing mechanisms

**H1 — existing path filters already cover Geant4 changes.** Eliminated by direct workflow inspection and #1192's zero-run witness.

**H2 — branch protection alone is sufficient.** Rejected. A required check that is never scheduled is not validation; it can instead leave the PR without the required status.

**H3 — adding `geant4/**` to both trigger events is the minimal routing repair.** Survives. It makes Geant4-only changes enter the existing required `test` lane.

**H4 — routing to MC Validation CI proves compiled Geant4 behavior.** Eliminated by inspection of the job: it installs Python dependencies, runs curated ruff, and runs non-integration pytest; there is no CMake/build/link/runtime Geant4 step.

Equivalent path-pattern variants that route the same complete `geant4/**` subtree are one mechanism class. Narrow lists such as `geant4/src_patch/**` are not equivalent because configs/macros/setup scripts are also material generator inputs.

## Falsifiers and execution

Implemented `tools/audit/validate_mc_ci_trigger_scope.py`, schema `ccb_mc_ci_trigger_scope_v1`, using `yaml.BaseLoader` so YAML 1.1 boolean coercion does not reinterpret the `on` key. It fails closed unless both events contain `geant4/**` and `jobs.test` exists.

Focused deterministic tests, no RNG:

1. repository workflow passes after repair;
2. missing `pull_request` Geant4 path raises a blocking error;
3. missing required `test` job raises a blocking error.

Supporting fixture execution before repository write: `python -m pytest -q tests/test_mc_ci_trigger_scope.py` -> `3 passed in 0.06s`; CLI validator -> `PASS`. Exact-head GitHub CI remains the authorising software check before merge.

# ARU-CI-G4-TRIGGER-001 — required validation routing for Geant4 and all PRs

**Stable concern:** `CI-G4-ROUTE-001`  
**Severity:** P0 for repository validation governance; not a detector/source-physics result.

## Atomic contract

Input: a Git change set and `.github/workflows/mc_validation_ci.yml`.  
Output: deterministic statement whether every pull request can produce protected-branch job `test`, and whether direct pushes changing `geant4/**` enter the same workflow.  
Units: none.  
State variables: event type, changed path, workflow path filters, job identifiers, exact commit SHA, workflow-run identity/conclusion.  
Scientific meaning: material generator/config/source changes must not escape or deadlock the repository's required static/Python validation lane. This atom does **not** assert compiled Geant4 validation.

Protected `main` requires `test`. GitHub's authoritative Actions documentation states that `paths` filters decide whether `push`/`pull_request` workflows run and that a workflow skipped by path filtering leaves an associated required check pending, blocking merge. The resulting invariant is:

```text
pull_request exists
and pull_request has neither paths nor paths-ignore
and geant4/** ∈ on.push.paths
and test ∈ jobs
```

The unfiltered pull-request condition subsumes enumerating `geant4/**` in a PR allow-list and removes the larger required-check/path-filter contradiction.

## Evidence inspected

- Pre-repair `mc_validation_ci.yml` requires job `test` but path-filters both `push` and `pull_request`, omitting `geant4/**`.
- PR #1192 exact head `bef24345e815152e22523a44b708c4359ad2958f` changes only `geant4/src_patch/ScatteringGenerator.cc`, `.hh`, and `patch_scatter.py`; GitHub reports no workflow runs for that exact head.
- #1192 is independently scientifically stale: its patch reintroduces `if(event->GetEventID()==0) EnsureFilesLoaded();`, undoing the per-instance first-use readiness already validated on main. Its separate pre-read file digest does not prove a digest of the exact consumed byte stream. The PR was closed, not merged.
- `geant4/setup_and_run.sh` still uses an unpinned/reused external `hibeam_g4` checkout and reused `build_conda`, so even a routed green Python/static CI result cannot become executable provenance.
- Authoritative GitHub Actions workflow-syntax and required-status-check documentation says a positive `paths` match schedules the workflow, while a workflow skipped by path filtering leaves its associated required check pending and blocks a PR that requires it.

## Competing mechanisms and equivalence collapse

**H1 — existing path filters already cover Geant4 changes.** Eliminated by direct workflow inspection and #1192's zero-run witness.

**H2 — branch protection alone is sufficient.** Rejected. A required check that is path-filtered out does not validate the commit and can remain pending.

**H3 — add only `geant4/**` to both PR/push allow-lists.** Locally repairs the immediate witness but is superseded by the stronger invariant: another material path omitted later would reproduce the same required-check deadlock. All finite allow-list variants share this mechanism.

**H4 — make the required `pull_request` event unfiltered, retain `geant4/**` in push routing.** Survives and is preferred. It makes every PR eligible to produce `test` while preserving direct Geant4-push routing.

**H5 — routing to MC Validation CI proves compiled Geant4 behavior.** Eliminated by inspection of the job: it installs Python dependencies, runs curated ruff, and runs non-integration pytest; there is no CMake/build/link/runtime Geant4 step.

## Falsifiers and execution

Implemented `tools/audit/validate_mc_ci_trigger_scope.py`, schema `ccb_mc_ci_trigger_scope_v2`, using `yaml.BaseLoader` so YAML 1.1 boolean coercion does not reinterpret the `on` key. It fails closed unless:

1. `push.paths` contains `geant4/**`;
2. `pull_request` is present and has neither `paths` nor `paths-ignore`;
3. `jobs.test` exists.

Deterministic negative controls, no RNG:

- missing `geant4/**` from push routing -> reject;
- any required-PR `paths` filter -> reject;
- missing/renamed `test` job -> reject.

Supporting exact fixture copy execution after the stronger model was derived:

`python -m pytest -q tests/test_mc_ci_trigger_scope.py` -> **4 passed in 0.05 s**.

`python tools/audit/validate_mc_ci_trigger_scope.py .github/workflows/mc_validation_ci.yml` -> **PASS**, `schema=ccb_mc_ci_trigger_scope_v2`, `pull_request.unfiltered=true`, `push.pattern_present=true`, `required_job=test`.

Exact-head GitHub CI remains the authorising repository software check before merge.
